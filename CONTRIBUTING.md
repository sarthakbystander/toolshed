# Contributing to Toolshed

Thanks for contributing! Toolshed is an open-source collection of independent web tools. This document explains how to add a tool and what the project expects of every contribution.

## Contribution workflow

```text
Create tools/<tool-name>/
        ↓
Add index.html
        ↓
Add tool.js / tool.css where needed
        ↓
Add tool.json
        ↓
Add README.md
        ↓
Add tests where appropriate
        ↓
Run npm run generate
        ↓
Run npm run verify
        ↓
Open Pull Request
```

**Important:** Never edit `registry/tools.json` by hand. It is generated from the `tool.json` files in `tools/`. Run `npm run generate` and commit the regenerated file.

## Tool structure

Every tool lives in its own directory:

```text
tools/
└── json-formatter/
    ├── index.html      # Required — the tool's page
    ├── tool.js         # Optional — tool logic (vanilla JavaScript)
    ├── tool.css        # Optional — tool-specific styles
    ├── tool.json       # Required — metadata (see contract below)
    ├── README.md       # Recommended — what the tool does and how to use it
    └── tests/          # Recommended — test files for the tool
```

Rules:

- The directory name is the tool's `id` and must be `lowercase-kebab-case` (no spaces, no uppercase, no random abbreviations). Examples: `json-formatter`, `image-compressor`, `color-converter`, `uuid-generator`, `markdown-preview`.
- The tool must be self-contained under its directory and load no external scripts from CDNs or third-party hosts.
- **Use the shared design system.** Link `../../assets/toolshed.css` in the page `<head>` (before any `tool.css`), reference the logo `../../assets/logo.svg` as the favicon,and reuse the site header/footer markup from existing tools. Add only tool-specific widget styles to `tool.css`;do not duplicate shared chrome. (External assets would be a review flag — see [SECURITY.md](SECURITY.md).)
- Tools run in the browser. Do not introduce a build step, a framework, or a Node.js runtime requirement for tools.
- The homepage will link to each tool at `tools/<id>/`, so keep the path stable once merged.

## Tool metadata contract

Each tool ships a `tool.json` manifest. The full JSON schema is in [scripts/generators/tool-schema.json](scripts/generators/tool-schema.json); the generator and verifier enforce it. The schema is designed to evolve: new fields should be added as *optional* properties so existing tools are never broken.

Example:

```json
{
  "id": "json-formatter",
  "name": "JSON Formatter",
  "description": "Format, validate and inspect JSON in your browser.",
  "category": "Developer",
  "tags": ["json", "formatter", "developer"],
  "version": "1.0.0",
  "runtime": "browser",
  "privacy": {
    "execution": "local",
    "dataUploaded": false,
    "storage": "none"
  }
}
```

Field reference:

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `id` | yes | string | Unique identifier. Must match the directory name and be `lowercase-kebab-case`. Used across the registry and in URLs. |
| `name` | yes | string | Human-readable name shown on the homepage and card. |
| `description` | yes | string | One or two sentences describing what the tool does. Shown in listings and search. |
| `category` | yes | string | Coarse grouping used for homepage sections (e.g. `Developer`, `Text`, `Image`). Keep the string short and consistent — reuse an existing category when one fits; propose a new one in the PR description. |
| `tags` | yes | string[] | Lowercase keywords for search. Keep them short and factual (e.g. `json`, `formatter`). No duplicates. |
| `version` | yes | string | Semantic version of the tool, `major.minor.patch` (e.g. `1.0.0`, `1.2.3`). |
| `runtime` | yes | string | Where the tool runs. Currently always `browser`. |
| `privacy.execution` | yes | string | Where the tool's logic executes. Currently always `local`. |
| `privacy.dataUploaded` | yes | boolean | `false` unless the tool deliberately transmits user input or derived data over the network. If `true`, the network behavior must also be documented in the tool's README and called out in the PR description. |
| `privacy.storage` | yes | string | One of `none`, `localStorage`, `sessionStorage`, `indexedDB` — where the tool persists data, if anywhere. |

Adding or changing the schema: update `scripts/generators/tool-schema.json`, the bundled validator in `scripts/generators/generate-registry.js`, this table, and [AGENTS.md](AGENTS.md). Keep every existing field backward compatible.

## Registry

```text
tools/*/tool.json
        ↓
generator
        ↓
registry/tools.json
        ↓
homepage / search / categories
```

The `tools/` directories are the source of truth. `registry/tools.json` is generated by `npm run generate` and committed so the static website can read it without a build step. Never edit it, and never duplicate tool metadata elsewhere in the repository.

## Privacy and security expectations

- Tools run locally in the browser whenever technically possible. Prefer `User → Browser → Tool` over `User → Toolshed server → Third-party API`.
- No hidden uploads, no unexpected network requests, no external scripts by default.
- Never hardcode private API keys into frontend code. If a tool legitimately needs a key, require the user to supply it in the browser.
- Any network request must be explicit, user-visible, and documented in the tool's `tool.json` and README.
- See [SECURITY.md](SECURITY.md) for the full policy.

## Verification

Run both commands from the repository root before opening a PR:

```bash
npm run generate   # regenerate registry/tools.json from tools/*/tool.json
npm run verify     # run repository health checks
```

Both must finish with exit code 0. CI runs the same commands on every push and pull request (see [.github/workflows/verify.yml](.github/workflows/verify.yml)).

### Verification pipeline (current → planned)

```text
Pull Request
    ↓
Schema validation            ← metadata validated against the tool.json contract
Tool structure validation   ← tools/ layout rules enforced
Metadata validation         ← bundled validator (generator + verifier)
Tests / linting              ← future: per-tool tests and linting
Security checks              ← future: dependency and script review
Link / asset checks          ← future: internal link and asset presence checks
Registry validation         ← registry/tools.json is fresh and deterministic
Website validation          ← homepage and required files exist
    ↓
PASS
```

The checks that are marked *future* are intentionally not faked today; they are added when the repository grows enough to make them meaningful.

## Repository tools (Node.js)

Node.js is used **only** for repository generators and verification. Tools themselves run in the browser and must not require Node.js. Keep `package.json` dependencies minimal — every dependency needs a reason.

## Code of conduct

Contributions are subject to our [Code of Conduct](CODE_OF_CONDUCT.md). Be respectful and constructive.

## Review checklist

Before opening a PR, confirm:

- [ ] `tools/<id>/` follows the required structure
- [ ] `tool.json` is valid per the contract (and the schema)
- [ ] No hand-editing of `registry/tools.json`
- [ ] `npm run generate` and `npm run verify` pass
- [ ] No frameworks, build steps, or browser-unsafe patterns introduced
- [ ] Any network behavior is documented in metadata and README
- [ ] No private keys or secrets anywhere in the code
