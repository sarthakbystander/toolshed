    How it works

    The auditor reads your manifest, works out which digest algorithm each line uses, hashes the files you select, and matches them by file name. Each manifest entry becomes one result row.

    • OK — the file's digest matches the manifest.
    • MISMATCH — the file was found but its digest differs. The file was modified or corrupted.
    • MISSING — the manifest lists the file but it was not among the files you provided.
    • EXTRA — the file was provided but is not listed in the manifest (optional, on by default).
    • UNKNOWN — the entry could not be verified, for example a digest-only record with no file name.

    Supported manifest formats

    • GNU coreutils output: sha256sum, md5sum, sha1sum, sha384sum, sha512sum, including the * binary-mode marker and \ escapes.
    • BSD / --tag output: SHA256 (file) = digest.
    • RFC 9530 HTTP Content-Digest: sha-256=:base64: (reported as an unverifiable digest-only record).
    • Plain digest filename lists, and two-column CSV in either order.
    • Unlabelled digests, where the algorithm is inferred from the digest length (32 = MD5, 40 = SHA-1, 64 = SHA-256, 96 = SHA-384, 128 = SHA-512).

    Privacy

    Files are read with the browser's File API and hashed in memory. Nothing is uploaded, no network requests are made, and nothing is written to storage. Close the tab and it is all gone.

    Limitations

    • Files are matched by name, not by path, so duplicate basenames in different folders are reported as ambiguous.
    • SHA digests use the browser's Web Crypto; MD5 uses a bundled implementation so it works even where MD5 is unavailable.
    • Folder selection uses the non-standard webkitdirectory attribute, supported by current Chrome, Edge, Firefox and Safari.
